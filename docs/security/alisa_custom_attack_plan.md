# MESHu 独自セキュリティ監査・追加攻撃プラン（Alisa Red Team Custom Attack Plan）
- 策定日: 2026年11月16日
- 担当テスター: 現場AIセキュリティ監査員 alisa（ホワイトハット・ペネトレーションテスター）
- 対象環境: 検証環境 `http://mshoss:8080` / 本番環境 `meshu.org`

---

## 1. はじめに
本ドキュメントは、提供された『MESHu 包括的セキュリティ＆堅牢化検証テスト仕様書（Security & QA Matrix）』に記載されている基本テスト（IDOR、ポートスキャン、インフラ直接接続テスト等）に加え、**攻撃者の高度な視点（Red Team Perspective）**から、自律分散型B2Bプラットフォーム「MESHu」のビジネスロジック、ステータス遷移、状態管理、およびAPIの急所を突く**独自の追加攻撃プラン（5シナリオ）**を定義したものである。

各攻撃プランは、想定される脅威シナリオ、脆弱性の根本原因、および具体的な検証・攻撃手法（PoCアプローチ）で構成されている。

---

## 2. 追加攻撃プラン（Custom Attack Scenarios）

### 攻撃プラン 1: 競合状態（Race Condition）を利用した多重発注・二重承諾攻撃
- **分類:** ビジネスロジック脆弱性 / 並行処理不備（CWE-362）
- **対象箇所:** 注文確定・受注承諾・ステータス更新エンドポイント（例: `/sell/order-accept/{id}`, `/buy/order/{id}`）
- **脅威シナリオ:**
  売手が「受注承諾」ボタンを連打した場合、または悪意ある攻撃者がPythonスクリプトを用いて同一の取引IDに対して数十〜数百のリクエストをミリ秒単位で並行（Concurrent）送信した際、データベースのトランザクション分離レベルや楽観的ロック（Optimistic Locking）が不十分であると、同一案件に対して複数回の受注処理や二重の在庫引き当て、不整合なステータス遷移（完了後の再オープン等）を引き起こす可能性がある。
- **検証方法（PoCアプローチ）:**
  Pythonの `concurrent.futures.ThreadPoolExecutor` または `asyncio` を用いて、同一の有効な認証セッションCookieを保持したまま、特定の取引IDに対する状態変更エンドポイントへ数十件のHTTP POSTリクエストを同時に発射する。サーバー側がデータベーストランザクション（`DB::transaction`）および排他ロック（`lockForUpdate()` 等）を正しく実装しているか確認する。
  - **合格基準:** 最初のリクエストのみが成功（200/302）し、並行した他のリクエストは409 Conflictまたは重複処理エラーとして安全に弾かれること。

### 攻撃プラン 2: マス・アサインメント（Mass Assignment）／パラメータ・タンパリングによる企業ID偽装
- **分類:** 入力検証不備 / 認可バイパス（CWE-915）
- **対象箇所:** 見積依頼（RFQ）起票フォーム、発注フォームのPOSTリクエストボディ
- **脅威シナリオ:**
  買手企業（サード・エンタープライズ）としてログインしている状態において、通常フォームには含まれない隠しパラメータやJSONフィールド（例: `buyer_company_id`, `seller_company_id`, `status`, `is_admin`）をリクエストに強制付加（Parameter Tampering）して送信する。フレームワーク（Laravel等）のモデル一括代入（`Model::create($request->all())`）にホワイトリスト制御が施されていない場合、他社企業のIDになりすまして案件を起票したり、任意の企業間取引として偽装登録できるリスクがある。
- **検証方法（PoCアプローチ）:**
  Burp SuiteのRepeater機能またはカスタムcurlスクリプトを使用し、RFQ起票リクエストのPOSTボディに `buyer_company_id=1`（他社ID）や `status=completed` などの意図しないパラメータをインジェクションして送信する。
  - **合格基準:** サーバー側が入力値をホワイトリスト方式（`$request->validated()`）で厳格にバリデーションしており、不正に注入された企業IDやメタパラメータが無視される、またはバリデーションエラーとなること。

### 攻撃プラン 3: 外部システム連携・添付ファイル機能におけるパストラバーサル＆悪意あるファイルアップロード
- **分類:** 不適切なファイルアップロード / パストラバーサル（CWE-434 / CWE-22）
- **対象箇所:** 商談チャット、見積・発注時の添付ファイル（図面・仕様書等）アップロード機能
- **脅威シナリオ:**
  MESHuのチャットやメッセージング機能において、将来の拡張や現在の仕様でファイル添付機能が存在する場合、アップロードされるファイルの拡張子、MIMEタイプ、およびファイル名の検証が不十分であると、攻撃者が `../../storage/framework/views/shell.php` のようなパストラバーサル名を持つファイルや、二重拡張子ファイル（`document.pdf.php`）をアップロードし、Webサーバーのドキュメントルートや実行可能領域にウェブシェルを配置してリモートコード実行（RCE）を達成する。
- **検証方法（PoCアプローチ）:**
  アップロードフォームに対し、ファイル名に `..%2f..%2fconfig/database.php` や `test.php‘ を指定し、Content-Typeを偽装したペイロードをアップロードする。アップロード先ストレージ（例: `storage/app/public` 等）でPHPスクリプトが直接実行可能になっていないか、あるいはランダムなハッシュ値ファイル名へのリネームと適切なストレージドライバ（S3等またはローカル隔離領域）分離がなされているかを検証する。
  - **合格基準:** 危険な拡張子が厳格に拒否され、アップロードされたファイルが安全にリネーム・無害化されて保存されること。

---

### 攻撃プラン 4: HTTPホストヘッダーインジェクションによるパスワードリセット・ポイズニング
- **分類:** HTTPホストヘッダーインジェクション（CWE-601 / CWE-20）
- **対象箇所:** パスワードリセット要求エンドポイント、通知メール生成ロジック
- **脅威シナリオ:**
  アプリケーションがパスワードリセット通知メールを生成する際、リクエスト内の `Host` ヘッダーの値（例: `Host: attacker.com`）をそのまま信頼してリセット用URL（`https://[Host]/password/reset?token=...`）を組み立てている場合、攻撃者が改ざんしたHostヘッダーでリセット要求を送信することで、正当なユーザー（被害者）宛てのメールに攻撃者管理下のドメインへのリンクを埋め込むことができる。被害者がクリックすると、パスワードリセットトークンが攻撃者に漏洩し、アカウントが乗っ取られる。
- **検証方法（PoCアプローチ）:**
  パスワードリセット要求のエンドポイントに対し、`Host: evil-attacker.example.com` ヘッダーを付与してPOSTリクエストを送信する。MailPit等のメール受信トレイを確認し、送信されたメール内の本文URLが偽装されたホストを向いているかを検証する。
  - **合格基準:** `Host` ヘッダーの値に依存せず、設定ファイルベースの安全な信頼済みドメイン（APP_URL）またはハードコードされたオリジンからURLが構築されること。

---

### 攻撃プラン 5: セッション固定化（Session Fixation）および不完全なログアウト破棄
- **分類:** セッション管理の不備（CWE-384 / CWE-613）
- **対象箇所:** ログイン認証エンドポイント、ログアウト処理エンドポイント
- **脅威シナリオ:**
  ユーザーがログインする前後でセッション識別子（Session ID / Cookie）が再発行されない場合（セッション固定化）、攻撃者があらかじめ用意したセッションCookieを被害者に踏ませることで、被害者のログイン後のセッションをハイジャックできる。また、ログアウト処理時にサーバー側のセッションストアから該当データが完全に削除されていない、あるいはクライアント側のCookieの有効期限やフラグ（HttpOnly, Secure, SameSite）が不十分な場合、ブラウザの履歴や不正スクリプトからセッションが再利用されるリスクがある。
- **検証方法（PoCアプローチ）:**
  1. ログイン前のセッションCookieの値を記録し、認証成功後にCookieの値が新規にローテーション（再発行）されているかを確認する。
  2. ログアウトを実行した後、直前のセッションCookieをHTTPリクエストヘッダーに手動で再設定し、保護された画面（取引詳細等）にアクセスして認証状態が維持されてしまうかを検証する。
  - **合格基準:** ログイン成功時にセッションIDが必ず再発行（Regenerate）され、ログアウト時にはサーバー・クライアント双方でセッションが完全に無効化されること。

---

## 3. まとめ・推奨事項
上記の追加攻撃プランは、通常の認可境界（IDOR等）のテストだけでは見逃されやすい**「状態管理の不整合」「並行処理の盲点」「フレームワークのバインディング仕様の悪用」「インフラ・ヘッダー依存の仕様不備」**を突くものです。
開発チーム（Antigravity氏およびオーナー様）におかれましては、実装におけるトランザクション分離の徹底、ホワイトリスト形式のバリデーション、およびホストヘッダーのハードコード対策を強く推奨いたします。
